# Диагностический протокол для следующего агента

[Обзор](../README.md) · [Хронология](timeline.md) · [Источники](evidence.md)

Цель — установить самый ранний доказанный барьер и проверить минимальное исправление. Этот репозиторий описывает завершённый опыт; чтение его не означает, что подключённый телефон нужно перепрошить.

## Выберите этап по свежим данным

| Наблюдение | Следующий полезный шаг | Критерий перехода дальше |
|---|---|---|
| Работает Android/root ADB | Проверить локально выбранную identity, build, boot completed, root и нужный симптом | Текущее состояние подтверждено; старые BROM-приёмники не используются |
| Только BROM/Preloader | Зафиксировать точный порт, protocol/version и первый отказ; найти совпадающий upstream-путь | Рукопожатие и identity реально подтверждены, не угаданы по VID/PID |
| `MDL=-1` / EMI ASSERT | Читать rank detection и выбранную запись; сравнить точные OEM-таблицы | Совместимая конфигурация прошла память и следующую стадию загрузки |
| GSI init reboot | Читать свежий last_kmsg; проверить фактически выбранную platform policy и property contexts | Компиляция, coverage типов и настоящий boot согласованы |
| Снимок роняет UI | Сохранить tombstone/BuildId; остановить повторные capture и найти upstream по стеку | Минимальный workaround подтверждён без нового падения SF |
| Часы/значки обрезаны | Сопоставить физическую панель и framework/SystemUI resources | Lookup и реальная видимость элементов проверены |
| Нет места под backup | Сначала инвентарь logical/allocated и канонических зависимостей | Проверенная распаковка/материализация прежде удаления raw |

## Порядок одного эксперимента

1. Зафиксируйте симптом, точный лог, build, входной программный hash и текущий режим. Device identifiers храните только локально.
2. Ищите готовое исправление у upstream по версии и строке отказа. Различайте совпадение подхода и готовый патч именно для этого файла.
3. Сформулируйте одну проверяемую гипотезу и отрицательный контроль. Например: «поменяли содержимое со старым hash — ROM обязан отвергнуть».
4. До записи проверьте точные preimage, размер, allowlist различий и доступный возврат. Используйте офлайн-аудит/эмуляцию, где это возможно.
5. Для физической записи требуется явная авторизация владельца, локальная привязка аппарата и актуальный проверенный backup. Разрешение публиковать отчёт не даёт разрешения прошивать другой телефон.
6. После записи прочитайте весь значимый объект и сравните, затем проверьте реальную следующую стадию. Reboot — отдельная проверка; настоящий cold power cycle — ещё одна.
7. Обновите checkpoint: что observed, что inferred, что unknown; где private evidence; какой следующий шаг разрешён.

## Ограничения, которые сохранили телефон и данные

- Выбирайте явный ADB target, затем проверяйте локальную привязку/identity. Не используйте «первое устройство». Приватный binding не переносится из этого репозитория.
- Не запускайте штатный `flash_all` вместо собственного проверенного плана: он может затереть исправленный preloader и содержать заводские действия.
- Не программируйте eFuse/RPMB-key ради устранения EMI ASSERT. Это не подтверждённая причина данного отказа.
- Не используйте `0x1001a0e0` как универсальный USBDL address. Для исследованного MT6768 установлен `0x1001a080`; другой SoC требует собственной карты.
- Не переносите service-LK offset в global-LK. [Таблица](gsi-policy.md#lk-два-разных-кандидата-разные-смещения) различает два файла.
- Для кнопочных действий нужна свежая готовность владельца, уже живой приёмник с heartbeat и явное время ожидания. Если доступен программный root-путь, используйте проверенный путь без кнопок.
- PIN/FRP/account verification проходит владелец. Не угадывайте PIN, не меняйте setup flags ради вида успешного завершения. Проверять Gmail можно без чтения писем.
- Перед UI-действием читайте свежий layout и проверяйте текущий пакет. Null root во время анимации означает ожидание/новую проверку, а не разрешение на старые координаты.
- Не считайте единичный ENOENT потока в procfs отказом USB. Локализуйте точную команду, сохраняя обязательные положительные проверки.
- Не публикуйте raw dumps, account screens, SSID, CID, серийные номера, IMEI, PIN, личные filesystem paths и их производные fingerprint-хеши. Программные hashes допустимы для точного сопоставления входов.

## Какой результат можно передать дальше

Укажите boot mode/slot, build, locale, root/SELinux, границы физических изменений, checksum/readback/reboot-проверки, состояние recovery и backups, известные отказы и непроверенное оборудование. Ссылка на «всё прошло» без этих условий не позволяет безопасно продолжить работу.

Для этого случая итог — работающий GSI A, проверенный Recovery B, два частных полных сжатых снимка, временные graphics/display fixes при запуске USB-помощника. Сотовая связь/полный hardware test остаются открытыми вопросами. Не возвращайтесь к восстановлению прошивки только потому, что читаете его историю.
